# FuturesArbBot

**Межбиржевой арбитражный робот для фьючерсов** на Python 3.14 с библиотекой [CCXT](https://github.com/ccxt/ccxt) (асинхронный клиент `ccxt.async_support`), консольным интерфейсом на [Rich](https://github.com/Textualize/rich) и менеджером пакетов [uv](https://docs.astral.sh/uv/).

Робот непрерывно опрашивает несколько криптобирж, сравнивает цены **линейных бессрочных фьючерсов (USDT-перпов)** по всем доступным торговым парам и находит расхождения, при которых одновременная покупка «там дешевле» и продажа «там дороже» приносит прибыль с учётом комиссий обеих бирж.

> ⚠️ **Дисклеймер.** Торговля фьючерсами с плечом — деятельность высокого риска. Данный проект — исследовательский инструмент, а не финансовый совет. Авторы не несут ответственности за финансовые потери. Всегда начинайте с режимов `DryRun` и `Testnet`.

---

## Возможности

- **Мониторинг всех доступных пар**: по умолчанию робот берёт все линейные бессрочные контракты в USDT (~1500–2000 инструментов на трёх биржах) с фильтром по обороту за 24 часа.
- **Арбитраж по «коридору спреда»**: два настраиваемых порога — вход при расхождении **вверх** (`min_spread_percent_up`) и фиксация прибыли при сжатии **вниз** (`min_spread_percent_down`), плюс стоп-лосс.
- **Фильтр по фандинг-рейту**: связка «лонг на дешёвой + шорт на дорогой» платит положительный рейт по лонгу и отрицательный по шорту, поэтому считается **чистый** фандинг пары (рейт шорта − рейт лонга). Если он строго ниже предела (`min_funding_rate_percent`, по умолчанию −1 %), фандинг «съедает» спред и сделка не открывается. Рейты кэшируются на 5 минут, при недоступности данных фильтр не блокирует сделки.
- **Учёт комиссий бирж**: нетто-спред = валовый спред − taker-комиссии **полного круга** (открытие обеих ног и их закрытие, то есть четыре комиссии) − буфер на проскальзывание. Комиссии автоматически подтягиваются из рынков CCXT (можно переопределить в конфиге).
- **Выбор режима сети**: `DryRun` (симуляция без ордеров) → `Testnet` (тестовая сеть биржи) → `Live` (реальная торговля, требует явного подтверждения).
- **Биржи через конфиг**: добавление/отключение биржи — одна строка в `exchanges.yaml`, без изменения кода.
- **Пары через конфиг**: белые и чёрные списки с wildcard-шаблонами (`BTC/USDT:*`, `*UP/USDT:*`).
- **Живой дашборд** в терминале: таблица лучших возможностей, журнал событий, строка статистики (Rich Live).
- **Ctrl+C — корректная остановка** с подробной статистикой сеанса: тики, тикеры, сигналы, сделки, PnL, топ символов, статистика по биржам, последние ошибки.
- **Защита от аномалий**: санитарный потолок спреда отсекает «фантомные» расхождения новых листингов и препаратов.
- **Настраиваемое исполнение заявок**: market / limit / chase-limit (догонание цены шагами), смещение цены в bps, time-in-force (включая post-only) и отдельные правила для закрытия — с автоматическим понижением до того, что биржа действительно поддерживает.
- **Модульная архитектура**: ядро не зависит от биржевой библиотеки, CCXT спрятан за адаптером `ExchangeConnector`; 160 модульных тестов (pytest).
- **Конфигурация в YAML, секреты в `.env`**: ключи бирж и токен бота не хранятся в репозитории; любой параметр можно переопределить переменной окружения.
- **Push-уведомления администратору в MAX Messenger**: найденный спред — тот же, что проходит `min_spread_percent_up` и фильтр по фандингу — приходит в лич чат бота. Отправка неблокирующая, с порогом, кулдауном на символ, лимитом в минуту и защитой от серии сбоев; настраивается отдельным необязательным файлом `config/notifications.yaml`.

## Как это работает

Каждые `refresh_interval_ms` миллисекунд (если опрос бирж укладывается в интервал) робот:

1. **Опрашивает биржи** (параллельно, с изоляцией ошибок): для Binance дополнительно досиливаются bid/ask из bookTicker, объём OKX извлекается из сырых данных.
2. **Фильтрует пары**: только линейные бессрочные фьючерсы, заданные котиры (USDT), минимальный оборот за 24 ч, белый/чёрный список, лимит `max_symbols` (берутся самые ликвидные).
3. **Ищет расхождения**: по каждому символу, присутствующему минимум на двух биржах, берётся пара «самая дешёвая цена покупки (ask) — самая дорогая цена продажи (bid)».
4. **Считает нетто-спред**:

```
валовый спред, %    = (bid_дорогой − ask_дешёвой) / ask_дешёвой × 100
нетто, %            = валовый − (taker_дешёвой% + taker_дорогой%) × 2 − проскальзывание%
```

> Множитель ×2 — комиссии закрытия: пару открывают двумя ногами и двумя ногами закрывают.
> Учитывать только открытие значит вдвое завышать доступный edge и пропускать сигналы, которые
> при честном расчёте убыточны уже на входе.

5. **Работает как коридор** (при включённой торговле `arbitrage.enabled: true`):

```
 нетто-спред, %
      ▲
  U ──┼──────── открываем арбитраж, когда спред пробил порог «вверх» (U)
      │        ╱╲        ╱╲
  D ──┼──────╱────╲──╱────── закрываем с прибылью при сжатии до порога «вниз» (D),
      │  ╱╱        ╲╲       но только если выход по текущим котировкам действительно в плюсе
  S ──┼───────────────────── стоп-лосс: если спред вырос до S — закрываем в убыток
      └──────────────────────► время
```

Позиция — дельта-нейтральная связка фьючерсов: **лонг на дешёвой бирже + шорт на дорогой**. Прибыль фиксируется при сжатии спреда, независимо от направления движения базового актива.

Важно: «спред сейчас» меряется теми же сторонами стакана, что и вход (bid дорогой − ask дешёвой), и потому оптимистичен на ширину обоих книг — закрывается же позиция по обратным сторонам (лонг продаётся по своему bid, шорт выкупается по своему ask). Поэтому перед фиксацией прибыли робот отдельно считает расчётный PnL немедленного выхода (зафиксированный на входе валовый спред − стоимость выхода − комиссии полного круга) и закрывает «в прибыль», только если он положителен. В строке открытия в журнале видно фактическую среднюю цену каждой ноги и её отклонение от котировки сигнала — по нему удобно сверять, не съедает ли исполнение весь edge.

Перед открытием каждая возможность проходит **фильтр по фандинг-рейту**: робот запрашивает актуальные рейты обеих бирж (кэш 5 минут) и считает **чистый** фандинг пары — рейт шорта минус рейт лонга. Смысл в знаках: при положительном рейте лонги платят шортам, поэтому наш лонг на дешёвой бирге платит, а наш шорт на дорогой получает; при отрицательном — всё наоборот. Если чистый фандинг строго ниже `min_funding_rate_percent` (по умолчанию −1 %), держание позиции обходится дороже спреда и сделка не открывается вовсе. Сравнивать рейты ног по отдельности нельзя: сильно отрицательный рейт по лонгу — это наша прибыль, а не риск. Если биржа не отдала рейт — сделка не блокируется (fail-open), а при постоянной недоступности в журнал пишется предупреждение. Фильтр влияет только на вход: закрытие, стоп и ребалансировка работают как раньше.

### Как исполняются сделки

- **Открытие** — двумя **marketable limit-ордерами**: покупка по ask дешёвой биржи, продажа по bid дорогой (лучше указанной цены не будет, но и проскальзывание за её пределы исключено). Тип заявки, смещение цены и догонание настраиваются разделом [`arbitrage.execution`](#тип-заявки-смещение-цены-и-догонание-arbitrageexecution). Ноги выставляются последовательно: **отказ первой ноги — вторая не выставляется вообще**.
- После приёма заявок робот ждёт **полного исполнения обеих ног** (`order_execution_timeout_ms`, опрос раз в `order_poll_interval_ms`). Если нога не доисполнилась, а политике положено догонание (`type: ChaseLimit`), заявка снимается и переставляется ближе к рынку — до `max_steps` раз в пределах `max_deviation_bps`, после чего остаток добивается market-ордером (`fallback_to_market`) либо ноги откатываются.
- Если нога отклонена, отменена или не доисполнилась за таймаут — живые заявки **отменяются**, а фактически набранный объём **откатывается** market `reduceOnly`-ордерами с ретраями. Позиция не регистрируется.
- Если откат пройти не мог (биржа «не отдаёт» объём), остаток **не теряется**: позиция регистрируется с фактическими раздельными объёмами ног (`long_size`/`short_size`) и передаётся циклу ведения.
- **Ребалансировка**: перекос ног сверх `rebalance_tolerance_percent` (но не меньше минимального лота биржи) устраняется обрезкой **бóльшей** ноги `reduceOnly`-заявкой — экспозиция и маржа не растут; тип и цена — по политике входа, остаток добирается на следующем тике.
- **Закрытие** (тейк/стоп/таймаут/выход) — по умолчанию market `reduceOnly` по фактическому объёму каждой ноги (`execution.close.type: Limit` — с ожиданием исполнения); если нога не закрылась, позиция остаётся в учёте и закрытие повторяется на каждом следующем тике.

## Архитектура

```
futures-arb-bot/
├── config/                          ← вся настройка здесь (YAML, перечитка «на лету»)
├── .env                             ← секреты: ключи бирж, токен бота (не коммитится)
├── scripts/                         ← run.cmd / run.ps1 / run.sh, test.ps1 / test.sh
├── src/futures_arb_bot/
│   ├── core/                        ← ядро: не знает ни о CCXT, ни о консоли
│   │   ├── domain/                  ← модели: тикеры, спреды, позиции, настройки,
│   │   │                               политика заявок (execution) и отчёты
│   │   ├── abstractions.py          ← протоколы: ExchangeConnector, TradeExecutor…
│   │   └── engine/                  ← сканер, калькулятор спредов, фильтр пар,
│   │                                   исполнитель сделок, статистика, журнал, уведомления
│   ├── infrastructure/
│   │   ├── ccxt_connector.py        ← адаптер CCXT (+ ccxt_factory.py — фабрика бирж)
│   │   ├── config.py                ← загрузка YAML + .env, переопределения, перечитка
│   │   └── max_messenger.py         ← клиент MAX Bot API
│   └── app/                         ← консоль: CLI, сборка зависимостей, баннер,
│                                       Live-дашборд, отчёт (rich)
├── tests/                           ← модульные тесты (pytest)
└── pyproject.toml, uv.lock          ← зависимости (uv)
```

Ключевые принципы:

- **Ядро чистое**: `futures_arb_bot.core` не зависит от CCXT — биржа подменяется реализацией протокола `ExchangeConnector` (в тестах — фейковая биржа). CCXT можно заменить на прямые REST API, не трогая логику.
- **Ошибка одной биржи не роняет сеанс**: биржи опрашиваются параллельно (`asyncio`) и изолированно, сбои логируются и учитываются в статистике.
- **Горячая конфигурация**: правки `appsettings.yaml`/`notifications.yaml` подхватываются без перезапуска (список бирж и фильтры пар — при перезапуске). Если при правке файл стал некорректным, робот продолжает работать на последней корректной версии.
- **Точная арифметика**: цены, объёмы, комиссии и PnL считаются в `Decimal`, без ошибок округления `float`.

## Установка и быстрый старт

```bash
git clone <репозиторий> futures-arb-bot
cd futures-arb-bot

uv sync                         # Python 3.14 + зависимости в .venv
cp .env.example .env            # заполните ключи (нужны только для торговли)

# 1) Одно сканирование: подключится к биржам и покажет возможности
uv run futures-arb-bot --once

# 2) Постоянный мониторинг с дашбордом
uv run futures-arb-bot

# 3) Без Live-дашборда (простой текстовый поток событий)
uv run futures-arb-bot --no-ui

# Запуск из другого каталога:
uv run futures-arb-bot --config-dir /путь/к/config
```

На Windows можно дважды щёлкнуть `scripts\run.cmd` или запустить `scripts\run.ps1` в PowerShell, на Linux/macOS — `./scripts/run.sh`. Скрипты передают роботу все аргументы: `scripts\run.cmd --once`.

Ключи API для мониторинга **не нужны** — тикеры это публичные данные. Ключи понадобятся, только когда включите торговлю.

### Docker

```bash
docker build -t futures-arb-bot .
docker run -it --rm --env-file .env futures-arb-bot --once
```

### Аргументы командной строки

| Аргумент | Описание |
|---|---|
| *(без аргументов)* | Постоянное сканирование с Live-дашбордом |
| `--once` | Одно сканирование, сводка, отчёт и выход |
| `--no-ui` | Без дашборда; события печатаются текстовым потоком |
| `--config-dir <путь>` | Каталог конфигурации (по умолчанию `./config`) |
| `--notify-test` | Проверить токен MAX и прислать тестовое сообщение в чат администратора (биржи не подключаются) |
| `--notify-chat-id` | Показать `chat_id`: отправьте боту любое сообщение, робот прочитает его из `/updates` |
| `--help` | Справка |

## Конфигурация

Весь конфиг — в каталоге `config/` в формате YAML. Три обязательных файла плюс один необязательный (`notifications.yaml`); изменения подхватываются «на лету».

**Имена ключей** — `snake_case`. Регистр и подчёркивания не важны, поэтому прежние имена (`MinSpreadPercentUp`) тоже понимаются.

**Секреты и переопределения — через `.env`** или обычные переменные окружения (уже заданные переменные `.env` не перекрывает):

| Переменная | Что задаёт |
|---|---|
| `ARB_<ID>_API_KEY`, `ARB_<ID>_SECRET`, `ARB_<ID>_PASSWORD` | Ключи биржи, например `ARB_OKX_PASSWORD` |
| `ARB_<РАЗДЕЛ>__<КЛЮЧ>[__<ВЛОЖЕННЫЙ>]` | Любой параметр YAML: `ARB_NOTIFICATIONS__BOT_TOKEN`, `ARB_GENERAL__NETWORK_MODE=DryRun`, `ARB_ARBITRAGE__EXECUTION__CHASE__MAX_STEPS=3`; элемент списка — по индексу: `ARB_EXCHANGES__ITEMS__0__ENABLED=false` |

`.env` ищется в текущем каталоге, в каталоге `config/` и над ним, а также в корне проекта.

### Тип заявки, смещение цены и догонание (`arbitrage.execution`)

Раздел **необязательный**: если его нет, робот ведёт себя как раньше — вход **marketable limit**
(по ask дешёвой биржи / по bid дорогой), закрытие **market**.

| Параметр | По умолчанию | Описание |
|---|---|---|
| `execution.type` | `Limit` (вход), `Market` (закрытие) | `Market` \| `Limit` \| `ChaseLimit` (лимитная заявка с догонанием цены) |
| `execution.limit_offset_bps` | `0` | Смещение цены от котировки в bps (1 bps = 0.01 %). `BUY` — выше (агрессивнее), `SELL` — ниже. Отрицательное значение = «пассивнее» |
| `execution.time_in_force` | `GTC` | `GTC` \| `Ioc` \| `Fok` \| `PostOnly` (post-only — заявка не должна разбрать стакан) |
| `execution.chase.mode` | `Simulated` | `Simulated` — перестановки делает робот; `Native` — chase-ордер биржи; `None` — обычная limit |
| `execution.chase.max_steps` | `5` | Сколько раз переставить заявку, прежде чем сдаться |
| `execution.chase.step_interval_ms` | `400` | Пауза между перестановками, мс |
| `execution.chase.step_bps` | `5` | Шаг смещения цены к рынку, bps |
| `execution.chase.max_deviation_bps` | `50` | Бюджет отклонения от стартовой цены; сверх него заявка не догоняется |
| `execution.chase.fallback_to_market` | `true` | `true` — добить остаток market; `false` — отменить и откатать набранное (как без chase) |
| `execution.chase.params` | — | Нативные параметры биржи для `mode: Native` (см. ниже) |
| `execution.close.*` | `type: Market` | Отдельная политика закрытия. `Chase` на закрытии не допускается — будет market |

Пример: вход chase-заявкой с шагом 5 bps, но не дальше 50 bps от котировки; закрытие — limit:

```yaml
arbitrage:
  order_execution_timeout_ms: 6000   # весь цикл догонания укладывается в этот таймаут
  execution:
    type: ChaseLimit
    limit_offset_bps: 2
    chase: { mode: Simulated, max_steps: 6, step_interval_ms: 350, step_bps: 5, max_deviation_bps: 60, fallback_to_market: true }
    close: { type: Limit, limit_offset_bps: 5 }
```

Переопределение на отдельную биржу (`exchanges.yaml`) — достаточно полей, которые отличаются:

```yaml
- id: bybit
  enabled: true
  execution: { limit_offset_bps: 15, chase: { max_steps: 2 } }
```

**Как работает догонание (`Simulated`).** Робот выставляет limit-заявку, ждёт `step_interval_ms`,
и если объём не набран — снимает заявку, фиксирует частичное исполнение и выставляет остаток
на шаг (`step_bps`) ближе к рынку. Так до `max_steps` раз, пока не упрётся в `max_deviation_bps`.
Дальше — market-добивка остатка (`fallback_to_market: true`) или отказ со стандартным откатом.
Средняя цена входа считается как средневзвешенная по всем заявкам ноги.
С `time_in_force: PostOnly` каждая перестановка тоже только мейкерская: если биржа отклонит
такую заявку (она разминулась со стаканом), нога считается мёртвой и включается обычный откат.
`ChaseLimit` вместе с `Ioc`/`Fok` не имеет смысла (остаток снимается сразу) — политика
понижает его до обычного `Limit` и сообщает об этом.

**Возможности бирж и безопасное понижение.** Перед стартом (`OrderConfigValidator`) и при
развёртывании политики (`OrderPolicyResolver`) неподдерживаемое не отправляется на биржу, а
понижается с предупреждением в журнал и в консоль:

| Биржа | Limit / cancel / fetch | Post-only (`timeInForce`) | IOC | FOK | Нативный chase |
|---|---|---|---|---|---|
| `binanceusdm`, `binance` | + | — | + | + | — |
| `bybit` | + | `PostOnly` | + | + | — |
| `okx` | + | `PO` | + | + | — |
| `gate` | + | `post_only` | + | — | — |
| `mexc` | + | — | — | — | — |
| `kucoinfutures` | + | — | + | — | **+** |
| `bitget` | + | `post_only` | + | + | — |
| `htx` | + | — | + | + | — |
| `bingx` | + | `PostOnly` | + | — | — |
| `coinex`, `phemex`, `krakenfutures`, неизвестные | + | — | — | — | — |

Примеры понижения: `ChaseLimit` + `mode: Native` на Binance → `Simulated`; `PostOnly` там же → `GTC`;
`ChaseLimit` на бирже без отмены заявок → обычный `Limit`; `ChaseLimit` вместе с `Ioc`/`Fok` →
обычный `Limit` (биржа сама снимает остаток, переставлять нечего). Таблица — это `ExchangeCapabilityMap`
(`src/futures_arb_bot/core/domain/order_execution.py`), её надо сверять при обновлении CCXT.

При старте робот печатает сводку по каждой бирже — какая заявка там реально будет использоваться
(после понижений) и что именно понижено:

```
· Binance USD-M Futures: вход — ChaseLimit (локальные перестановки: до 5 шагов по 5 bps, не дальше 50 bps от старта, остаток — market), закрытие — Market
! Binance USD-M Futures: нативный chase на binanceusdm недоступен — используется локальное догонание (Simulated)
· KuCoin Futures: вход — ChaseLimit (нативный chase биржи, параметры: chaseType), закрытие — Market
```

**Нативный chase (`mode: Native`) — опция «для тех, кто проверил».** Робот выставляет такую заявку
через единый `createOrder` CCXT, добавляя в `params` содержимое `execution.chase.params` как есть.
Гарантии, что биржа поймёт её именно как chase, тут нет: у KuCoin Futures «догоняющий» ордер в CCXT
вынесен в отдельный неявный метод `contractPrivatePostOrderChaseLimitOrder`, и единый `createOrder`
туда не ходит. Поэтому `Native` обязан быть проверен на testnet по документации своей биржи
(имена параметров + факт догонания цены), а до проверки разумно использовать `Simulated`.
Если `params` пустой, политика сама понизит режим до `Simulated` и сообщит об этом.
При `Native` робот не делает локальных перестановок: выставляется одна заявка, а её исполнением
биржа занимается сама — робот ждёт до `order_execution_timeout_ms`, затем отменяет и откатывает набранное.

```yaml
# только после проверки на testnet: mode = Native требует непустого params
execution:
  type: ChaseLimit
  chase: { mode: Native, fallback_to_market: false, params: { chaseType: priceChase } }
```

### Сверка лимитов с биржей

Лимиты `max_open_positions` и `max_positions_per_exchange` считаются не только по позициям текущего сеанса, но и по **фактической экспозиции на биржах**. Перед каждым сканом возможностей (не чаще раза в минуту — `fetchPositions` это приватный запрос) робот опрашивает позиции каждой подключённой биржи:

- **Позиции вне учёта сеанса занимают слоты лимитов.** Символ с ненулевой экспозицией сразу на двух и более биржах засчитывается как внешний арбитраж (`max_open_positions`), каждая отдельная «одиночная» нога занимает слот своей биржи (`max_positions_per_exchange`). После рестарта бот не откроет «ещё одну» сделку поверх оставшейся на биржах связки.
- **Свои позиции не считаются дважды** — символы позиций, которые робот ведёт в этом сеансе, исключаются из снимка сверки.
- **Чужая одноногая экспозиция** (например, лонг по `X/USDT` только на одной бирже) занимает один слот `max_positions_per_exchange` этой биржи, но не слоты других бирж и не слот арбитража.
- **При сбое сверки** сохраняется последний известный снимок экспозиции — слоты лимитов не «освобождаются» из-за сетевой недоступности биржи; о сбое пишется предупреждение в журнал (одно на биржу).
- **В `DryRun`** сверка пропускается: заявок в симуляции нет, сверяться не с чем.
- Если `fetchPositions` не поддерживается биржей (ошибка в журнале), лимиты по этой бирже считаются только по позициям сеанса.

От «потерь» учёта цикл ведения дополнительно защищает ещё две ситуации:

- **Неотменённые при откате открытия заявки не забываются**: каждый тик робот пробует отменить их снова, пока они живы в стакане; если такая заявка самоисполнилась — символ занимает слот внешней экспозиции до закрытия.
- **Закрытие market-ордером засчитывается только подтверждённым**: по исполненному объёму в статусе заявки (`fetchOrder`) либо по отсутствию позиции в `fetchPositions`. Без подтверждения нога считается открытой, позиция остаётся в учёте, и закрытие повторяется на следующем тике.

### `exchanges.yaml` — биржи и ключи

Каждая запись списка `exchanges.items`:

| Поле | Описание |
|---|---|
| `id` | Идентификатор CCXT: `binanceusdm`, `bybit`, `okx`, `gate`, `mexc`, `kucoinfutures`, `bitget`, `htx`, `coinex`, `phemex`, `krakenfutures`, `bingx` |
| `name` | Отображаемое имя (произвольное) |
| `enabled` | `true`/`false` — включить биржу (нужно минимум две) |
| `api_key`, `secret`, `password` | Ключи для торговли — **лучше в `.env`** (см. ниже). `password` нужен OKX/KuCoin/Bitget (passphrase) |
| `taker_fee_percent`, `maker_fee_percent` | Переопределение комиссии в % (иначе — с биржи) |
| `options` | Дополнительные опции CCXT для биржи |
| `execution` | Переопределение политики заявок для этой биржи — только отличающиеся поля ([подробнее](#тип-заявки-смещение-цены-и-догонание-arbitrageexecution)) |

> **Секреты.** Не держите ключи в репозитории. Задайте их в `.env` (шаблон — `.env.example`):
> `ARB_<ID>_API_KEY`, `ARB_<ID>_SECRET`, `ARB_<ID>_PASSWORD` (например, `ARB_BYBIT_API_KEY`).
> Если ключ задан и в `exchanges.yaml`, приоритет у значения из файла.

Встроенные биржи: `binanceusdm` (Binance USD-M), `binance`, `bybit`, `okx`, `gate`, `mexc`, `kucoinfutures`, `bitget`, `htx`, `coinex`, `phemex`, `krakenfutures`, `bingx`.

> **Особенности BingX (`bingx`).** Робот ставит CCXT-опцию `defaultType: swap` (перпетуалы), символы — unified-вид `BTC/USDT:USDT`.
> Плечо отправляется с параметром `side: BOTH`, поэтому счёт на бирже должен быть в режиме **one-way** (односторонний);
> в hedge-режиме заявке нужен `positionSide`, которого в политике робота нет. `timeInForce` принимает `GTC`, `IOC`,
> `PostOnly` (FOK — нет), поэтому `ChaseLimit` догоняет сам исполнитель (отмена + перестановка). Тестовая сеть —
> demo-счёт BingX с отдельными API-ключами (`ARB_BINGX_API_KEY` / `ARB_BINGX_SECRET`), в sandbox доступны только свопы.

<details>
<summary>Как добавить биржу, которой нет в списке</summary>

1. Откройте `src/futures_arb_bot/infrastructure/ccxt_factory.py` и допишите id биржи CCXT в кортеж `SUPPORTED`.
2. Добавьте возможности биржи в `ExchangeCapabilityMap` (`src/futures_arb_bot/core/domain/order_execution.py`) — тест `tests/test_exchange_wiring.py` проверяет, что фабрика и карта согласованы.
3. Перезапустите робота. Класс биржи берётся из `ccxt.async_support`; список всех 100+ бирж — `ccxt.exchanges`.
</details>

### `symbols.yaml` — торговые пары

По умолчанию: **все** линейные бессрочные фьючерсы в USDT с оборотом от 5 млн USDT/сутки, максимум 400 самых ликвидных.

| Параметр | По умолчанию | Описание |
|---|---|---|
| `quote_currencies` | `[USDT]` | Котиры (например, `[USDT, USDC]`) |
| `min_quote_volume24h_usd` | `5000000` | Минимальный оборот за 24 ч, USDT |
| `max_symbols` | `400` | Предел числа отслеживаемых пар (берутся самые ликвидные) |
| `max_ticker_age_seconds` | `15` | Устаревшие тикеры не участвуют в расчёте |
| `max_ticker_skew_seconds` | `5` | Не сравнивать котировки двух бирж, если они сняты с разницей больше этого времени (иначе «спред» мог породить лаг опроса, а не рынок) |
| `include` | `[]` | **Белый список** шаблонов (если не пуст — только эти пары) |
| `exclude` | `[]` | **Чёрный список** шаблонов |

Шаблоны поддерживают `*` (любая последовательность) и `?` (один символ), без учёта регистра:

```yaml
include: ["BTC/USDT:*", "ETH/USDT:*"]      # только BTC и ETH
exclude: ["*UP/USDT:*", "1000*/USDT:*"]    # без леверидж-токенов и 1000X-вариантов
```

> Unified-символ CCXT выглядит как `BTC/USDT:USDT` (базис/котиры:сеттлмент). Совпадение пар между биржами идёт по этому имени, поэтому `1000PEPE/USDT:USDT` на одной бирже не «склеится» с `PEPE/USDT:USDT` на другой — используйте `exclude`/`include`, если это мешает.

### `notifications.yaml` — уведомления администратору в MAX Messenger

Файл **необязательный**: если его удалить или оставить `enabled: false`, робот работает как раньше — только с журналом в консоли и в `logs/`. Уведомление приходит, когда спред прошёл *обе* существующие проверки: `arbitrage.min_spread_percent_up` и фильтр по фандинг-рейту. Сделки, стопы, ошибки и итоги сеанса в мессенджер не шлются.

| Параметр | По умолчанию | Описание |
|---|---|---|
| `enabled` | `false` | Главный выключатель раздела |
| `bot_token` | `""` | Токен бота. Секрет: лучше задавать в `.env`: `ARB_NOTIFICATIONS__BOT_TOKEN` |
| `admin_chat_id` | `""` | `chat_id` диалога администратора — см. «Как получить chat_id» |
| `api_base_url` | `https://platform-api2.max.ru` | База Bot API v2 (старый `platform-api.max.ru` тоже принимается) |
| `endpoint` | `Messages` | `Messages` → `POST /messages?chat_id=…`; `ChatsMessage` → запасной `POST /chats/{chat_id}/message` |
| `min_spread_percent` | `null` | Дополнительный порог «не уже, чем». `null` — наследует `arbitrage.min_spread_percent_up` |
| `use_markdown` | `false` | Отправлять с `format: "markdown"` (в шаблоне тогда уместны `*звёздочки*`) |
| `silent` | `false` | `true` → `notify: false`: сообщение без push-звука |
| `signal_cooldown_seconds` | `120` | Не чаще одного сообщения на символ |
| `max_per_minute` | `20` | Скользящий лимит на все сообщения (защита от шквала по многим парам) |
| `timeout_ms` | `5000` | Таймаут одного HTTP-запроса |
| `max_retries` | `3` | Повторы внутри транспорта при 429/5xx/сети (учитывается `Retry-After`) |
| `failure_circuit_limit` | `5` | Столько неудач подряд — и канал закрывается (в поставке — `1`) |
| `circuit_break_minutes` | `10` | На сколько минут закрывается; при 400/401/403/404 — сразу (в поставке — `2`) |
| `queue_capacity` | `64` | Вместимость очереди (читается при старте); переполнение — сигнал отбрасывается |
| `text_template` | встроенный | Шаблон текста, см. подстановки ниже |

Подстановки шаблона: `{symbol}` `{longExchange}` `{longPrice}` `{shortExchange}` `{shortPrice}` `{net}` `{gross}` `{longFee}` `{shortFee}` `{longFunding}` `{shortFunding}` `{volume}` `{time}`.

#### Как настроить

1. **Создайте бота**: откройте диалог с `@MasterBot` в Max и следуйте инструкциям — Master Bot пришлёт токен.
2. **Запишите токен** в `.env` (не в YAML):
   ```dotenv
   ARB_NOTIFICATIONS__BOT_TOKEN=86:xxxxx
   ```
3. **Узнайте `chat_id`**: бот Max **не может написать первым**, поэтому сначала сами напишите боту любое сообщение, а затем:
   ```bash
   uv run futures-arb-bot --notify-chat-id
   ```
   Робот слушает `/updates` до 90 секунд и печатает `chat_id` диалога. Запишите его в `.env` (`ARB_NOTIFICATIONS__ADMIN_CHAT_ID=…`) или в `admin_chat_id`.
4. **Проверьте канал**:
   ```bash
   uv run futures-arb-bot --notify-test
   ```
   Команда показывает разобранные настройки (токен — в виде маски), вызывает `GET /me` и присылает тестовое сообщение; биржи при этом не подключаются.
5. **Включите раздел**: `enabled: true` в `config/notifications.yaml` — можно на лету, без перезапуска.

В журнале сеанса всегда видна строка состояния: `Уведомления в MAX: включены (чат …, порог …, не чаще одного на символ в … с)` или предупреждение, что `BotToken`/`AdminChatId` не заданы.

> Доставка настроена «best effort»: фоновая очередь не блокирует цикл сканирования, а постоянная ошибка (неверный токен, закрытый диалог) не позволяет роботу долбить мессенджер — канал приостанавливается на `circuit_break_minutes` и снова открывается сам.

## Режимы сети

| Режим | Что происходит | Ключи |
|---|---|---|
| **DryRun** | Полный цикл сканирования; «сделки» симулируются по текущим bid/ask, PnL считается виртуально. Идеально для проверки настроек | не нужны |
| **Testnet** | Реальные ордера на тестовой сети биржи (`set_sandbox_mode`), условные деньги | тестнет-ключи биржи |
| **Live** | Реальные ордера на реальные деньги | боевые ключи + `arbitrage.allow_live: true` |

Чек-лист включения реальной торговли:

1. `general.network_mode: Testnet` (сначала!), `arbitrage.enabled: true`, ключи в `.env` (`ARB_*`-переменные).
2. Запуск — робот сам проверит ключи приватным запросом (`fetch_balance`).
3. Отработайте хотя бы день на Testnet, только потом `network_mode: Live` + `arbitrage.allow_live: true`.
4. Начните с малого `order_size_usd` и большого `min_spread_percent_up`.

Защита от опечаток: в режиме Live без `allow_live` робот **откажется запускаться**; при невалидных ключах торговля не включится.

## Управление

- **Ctrl+C** — корректная остановка: сканер завершает текущий тик, позиции закрываются (если `close_positions_on_exit`), после чего печатается **подробный отчёт сеанса**:
  - режим, длительность, тики, тикеры, сигналы (и в час), лучший спред за сеанс;
  - таблица закрытых арбитражей с PnL по каждому и итоговая PnL (с учётом комиссий);
  - позиции, оставшиеся открытыми;
  - статистика по биржам: рынков, запросов, ошибок, средняя задержка, taker-комиссия;
  - гистограмма «топ символов по числу сигналов»;
  - последние ошибки.
  Повторный Ctrl+C — принудительное завершение.
- **Журнал** дублируется в `logs/session-YYYYMMDD-HHmmss.log` (все уровни, включая Debug).

То же одной командой: `scripts\test.ps1` (Windows) или `./scripts/test.sh`.

Структура тестов: калькулятор спредов (математика комиссий, санитарный потолок), фильтр пар (wildcards, котиры, объёмы), исполнитель (симуляция открытия/закрытия, PnL, стоп-лосс, защита от дублей), limit-исполнение (отказ/частичное исполнение/таймаут ног, откаты, ребаланс, поноговое закрытие), принудительное исполнение лимитов (сверка с биржей, внешняя экспозиция, неподтверждённое market-закрытие, неотменённые заявки откатов), статистика, форматы чисел, уведомления (шаблон текста, порог/кулдаун/лимит в минуту и защита от сбоев в отправителе, HTTP-слой MAX с заготовленным транспортом), загрузка YAML-конфигурации (необязательный `notifications.yaml`, переопределения из окружения, перечитка «на лету»), проводка бирж (каждая биржа фабрики есть в карте возможностей и создаётся CCXT).

## FAQ

**Почему сигнал есть, а робот не торгует?** — По умолчанию `arbitrage.enabled: false`: это монитор. Включите торговлю и пройдите чек-лист режима сети.

**Вижу спред 3 %, а робот молчит.** — Проверьте `max_spread_percent` (аномалии отбрасываются), нетто-спред с учётом комиссий (может уйти в минус), объём и `min_quote_volume24h_usd`.

**Лимиты свободны, а новые арбитражи не открываются.** — Робот считает не только позиции текущего сеанса, но и фактическую экспозицию на биржах (см. [Сверка лимитов с биржей](#сверка-лимитов-с-биржей)). Остатки после рестарта или ручные сделки под теми же ключами занимают слоты — ищите в журнале предупреждение «На биржах найдены позиции вне учёта этого сеанса».

**Реально ли заработать на межбиржевом арбитраже?** — Чистые расхождения на топ-биржах редки и малы (обычно < 0.2 %). Плюс: задержки сети, проскальзывание, лимиты бирж, перевод денег между биржами. Робот показывает реальную картину с учётом комиссий — решать вам.

**Что такое «стоковые перпы» (AAPL, TSLA на Binance)?** — В 2025–2026 биржи начали листить бессрочные контракты на акции. Их цены на разных биржах считаются от разных индексов, поэтому «спреды» между ними фиктивны — санитарный потолок `max_spread_percent` их отсекает.

**Можно ли добавить спот?** — Да: реализуйте протокол `ExchangeConnector` (или разрешите спот-рынки в коннекторе) — ядро менять не нужно. Но проект сфокусирован на фьючерсах.

**Много запросов к бирже?** — Тик запускается не чаще раза в `refresh_interval_ms`; каждый тик — `fetch_tickers` и `fetch_bids_asks` на каждую биржу (фандинг — раз в 5 минут), сверху это дополнительно ограничивает rate limiter CCXT (`enableRateLimit`). При 3 биржах и интервале 2 с это ~3 запроса/с; не ставьте интервал меньше 1 с без нужды.

## Ограничения и риски

- Открытие исполняется **limit-ордерами** — риск не исполниться покрывается таймаутом с отменой и откатом; закрытие/откаты — **рыночные ордера**, на неликвидных парах возможно проскальзывание (буфер `slippage_buffer_percent` и фильтр объёма снижают, но не устраняют риск).
- **Догонание цены (`ChaseLimit`) — компромисс скорости и цены.** Каждый шаг — это отмена + новая заявка, поэтому растёт число запросов к бирже (нужен запас по rate limit) и среднее время открытия; при `fallback_to_market: true` остаток добирается по market-цене, то есть «гарантия исполнения» оплачивается проскальзыванием. Весь цикл догонания укладывается в `order_execution_timeout_ms` — если бюджета шагов не хватает, заявка снимается.
- **Нативный chase (`chase.mode: Native`) помечен как непроверенный**: имена параметров берутся из документации конкретной биржи и обязаны быть подтверждены на testnet до Live. Пока параметры не заданы, политика сама понижает режим до `Simulated`, а возможности бирж заданы таблицей `ExchangeCapabilityMap` — при обновлении CCXT её нужно сверять.
- `PostOnly`, `IOC`/`FOK` поддерживаются не всеми биржами: неподдерживаемое условие понижается до `GTC` с предупреждением (см. таблицу возможностей бирж).
- PnL и комиссии по-прежнему считаются по **taker**-ставке: даже если заявка исполнена как maker (post-only/chase), прибыль в отчёте занижена. Учёт `taker/maker` по фактическому исполнению — отдельная задача (нужно разбирать поле `takerOrMaker` из ответов CCXT).
- Сетевые задержки: между «сигналом» и исполнением второй ноги цена может уйти — несобранная связка откатывается автоматически (`reduceOnly`, с ретраями), а её остатки не бросаются, а регистрируются позицией и ребалансируются/закрываются циклом ведения.
- Частичные исполнения отслеживаются раздельно по ногам; перекос сверх `rebalance_tolerance_percent` устраняется обрезкой бóльшей ноги (limit `reduceOnly`).
- PnL считается по ценам исполнения биржи; комиссии — оценочно по taker-ставке (детальные комиссии биржи не парсятся).
- Одна арбитражная позиция на символ; маржа не резервируется заранее — робот ловит ошибку `InsufficientFunds` и пропускает сделку.
